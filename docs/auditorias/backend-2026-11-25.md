## Hallazgo 1 (Alta) — Dedupe con fugas: 77 correos repetidos en contactos activos

**Consulta:**

```sql
select count(*) as correos_repetidos, coalesce(sum(c),0) as contactos_implicados from (
  select lower(trim(email)) e, count(*) c from contacts
  where deleted_at is null and email is not null and email <> ''
  group by 1 having count(*) > 1) t;
-- → [{"correos_repetidos":77,"contactos_implicados":"154"}]   (idéntico a las corridas 01:12 y 03:12)
```

Pares sistemáticos id N / N+300 con el mismo correo (p. ej. id 1 y id 301, `ana.ruiz@cristalesnorte.com`): provienen de la semilla demo (ciclo de 300), no de una importación con fuga. La base no lo impide: el único índice por correo es `contacts_email_idx … USING btree (lower(email)) WHERE (deleted_at IS NULL)` — **no único** (verificado en `pg_indexes` en esta corrida).

**Impacto real sobre el motor de importación** (`src/import-engine.js`, `planImport`, línea 405, verificada hoy): el índice `byKey` conserva solo el **primer** registro por correo (`if (k && !byKey.has(k)) byKey.set(k, c)`). Una importación en modo «Crear y actualizar» cuyo archivo contenga `ana.ruiz@cristalesnorte.com` actualizará el id 1 y dejará el id 301 intacto, sin error ni aviso; el monitor reportará «1 actualizado» y será cierto, pero el otro duplicado queda obsoleto. La pantalla de revisión de duplicados tampoco avisa de la ambigüedad (a diferencia de empresas, donde sí existe `MULTIPLE_COMPANIES_WITH_DOMAIN`).

**Nota:** los dominios de empresas están limpios (0 duplicados).

## Hallazgo 2 (Media) — `created` falso en todos los registros creados desde la app

**Código (verificado hoy):** `src/data.js:493` → `export const TODAY = new Date(2026, 10, 7)` (fecha fija); `addRecord` persiste `created: TODAY.toISOString()`. Los valores por defecto de importación (`newRecordDefaults`, import-engine.js líneas 705-714) también sellan `lastActivity` con `TODAY`.

**Evidencia de la base (idéntica a la corrida anterior):**

```sql
-- registros con created = '2026-11-07 06:00%' / total:
-- contacts 4/423 · companies 4/40 · deals 1/150 · tickets 3/84 · tasks 0/64
```

Registros con actividad real del 19 al 23 de noviembre (contactos 1, 422 y 423) llevan `created = 2026-11-07 06:00 UTC`: el sello es artificial.

**Impacto:** «Fecha de creación del objeto» miente en listas, fichas y ordenaciones; los importados reciben `lastActivity` = 7-nov aunque nunca se hayan tocado; cualquier vista filtrada por creación reciente excluye registros reales. No hay pérdida de datos, pero sí datos incorrectos persistentes en los 4 módulos.

## Hallazgo 3 (Media) — Historial de importaciones sin contraparte auditable en la base

**Consultas (idénticas a la corrida anterior):**

```sql
select count(*) total, max(id) ultimo from import_jobs;
-- → [{"total":0,"ultimo":null}]

select key from user_settings where key like 'crm:imports%'
union all select key from account_settings where key like 'crm:imports%';
-- → [] (vacío)

-- Sellos de importación en registros:
-- activos: 0 en los 4 módulos; papelera: companies 47 (sello 1795365487574) y 56 (sello 1795413053517)
```

**Diagnóstico:**

1. La tabla `import_jobs` no conserva **ninguna** fila. Los dos sellos corresponden a corridas SMOKE cuyas filas se borraron con el usuario desechable (`removeLiveUser` en `scripts/smoke-live.mjs`; correctamente acotado, no toca al usuario real).
2. La limpieza smoke dejó residuo: las 2 empresas de la papelera siguen físicamente en la base con sello de importación cuyo historial ya no existe. Además, ningún registro activo conserva sello: el mecanismo «Ver segmento» de importaciones no tiene hoy ningún registro real al que apuntar.
3. El monitor (`src/integration.js`) lee `importHistory()` = localStorage + settings. Al no existir nada durable, **los conteos del monitor no se pueden cruzar con la base**: esta auditoría solo pudo verificar el lado SQL. Si el navegador del usuario pierde localStorage, el historial (y el ledger de «Deshacer importación») se pierde con él. La migración perezosa de `import-jobs.js` (`init`) solo sube lo que exista en el navegador que la ejecuta.

**Lo que sí está bien:** la escritura a `import_jobs` funciona cuando corre — `smoke-import-jobs.mjs` pasa (migración idempotente, conteos, sesión fresca, ledger, reintentos y RLS por equipo), verificado de nuevo en esta corrida.

## Hallazgo 4 (Baja) — Sincronización de apps: real pero nunca ejercida en esta cuenta

**Evidencia (idéntica a la corrida anterior):**

```sql
-- app_sync_state: 0 filas · connected_accounts: 1 (gmail, fernando-lovera@megaglass.us, activa)
-- activities con extra->>'source'='gmail': 0 · tasks con extra->>'source'='gcal': 0
```

**Diagnóstico:** no hay datos simulados ni botones muertos en `src/integration.js` / `src/app-sync.js` (código releído hoy): `loadApps` lee `connected_accounts` + `app_sync_state` reales; «Sincronizar ahora» llama a la Edge Function `app-sync`, que confirma atómicamente vía RPC `commit_app_sync`. Las apps sin scope (WhatsApp, Outlook, Mailchimp, Zapier, QuickBooks) se muestran como «Disponible próximamente» **sin** botón de conectar, y «Data Hub» avisa que no está disponible — comportamiento honesto, no simulado.

El riesgo es de verificación: con `app_sync_state` vacío y 0 filas sincronizadas, nunca se ha completado un lote real en esta cuenta; la única evidencia de que la escritura funciona es `smoke-app-sync.mjs` (PGlite + harness del edge), que pasa. Además, la cuenta conectada no tiene el scope `calendar.events.readonly`, así que Google Calendar correctamente aparece como no conectada.
